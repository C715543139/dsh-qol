# 连体消息导航按钮特定位置点击无反应

日期：2026-10-11

## 现象

在部分滚动位置点击「上一条」或「下一条」没有反应；手动拖动内容几像素后再次点击恢复正常。

## 根因

第一版修复只覆盖了“目标被 clamp 成原地”的情况，但本次实机反馈是另一种死区：消息「我希望」的顶部大约在滚动视口顶部下方 33~50px。旧的 `jumpToNextUserMsg()` 取“第一条 `top > viewTop + 16` 的用户消息”作为目标，因此把**当前正在看的消息自己**当成目标，只滚动 `top - 16`，实际移动约 17~34px。平滑滚动下这段位移肉眼近似没有反应；手动把滚动条向下拖一点后，该消息越过视口顶边，退出候选扫描，下一条用户消息才成为目标，于是突然出现大幅滚动。

宿主滚动容器不是本次根因：宿主 CSS 明确规定普通布局下 `[data-conversation-scroll]` 为 `overflow-y:auto`，其内 `.EvIC1a_scroll` 为 `overflow:visible`。

## 修复

- 上半按钮逻辑不变，保留既有顶对齐与 clamp 防护。
- 下半按钮改为与上半同构的“当前行 → 后一行”：当前行优先取顶对齐行，否则取视口中心之上的最后一条用户消息；目标取它的后一条。
- 没有中心之上的消息时，把第一条用户消息作为下一条；越过最后一条时按原有逻辑滚到底部。
- 宿主在运行中插入/排队的用户输入会标成 `data-chat-flow-kind="steering"`，它仍是用户可见消息；导航候选现在统一包含 `user` 和 `steering`，因此上下两个方向都不会漏掉这类消息。
- 保留 16px 落点偏移、平滑滚动和 reduced-motion 行为；密集行仍有向后跳过 clamp 落点的守卫。

## 验收标准

1. 在消息间距很小、消息顶边刚好落在当前落点附近时，连续点击上下按钮，每次都应发生滚动或明确到达顶/底，不需要先手动拖动。
2. 普通长会话中，上下按钮仍逐条移动一条用户消息。
3. `npm run build` 通过。
